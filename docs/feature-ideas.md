# Идеи развития Skerry (черновик, не коммитить)

Брейншторм 2026-07-23. Ключевые утверждения про клиент сверены с кодом
(что уже есть / чего нет); серверные пункты — по известным багам и PR,
перед реализацией перепроверить по `server/` и sync-движку.

## Крупная ставка №1: RDP-клиент

Прямое продолжение VNC: тот же UX-слот «удалённый рабочий стол», но RDP кратно
востребованнее в корпоративе, куда Skerry метит против Termius / Royal TS.

- Стоимость: высокая — свой RDP-стек либо FreeRDP через JNA (desktop) и NDK (Android);
  Android-сборка FreeRDP — основной риск, недели работы.
- Ценность: после этого клиент закрывает *все* типовые «подключиться к машине».
- Когда: следующий крупный подход, после того как VNC доедет до релиза и обкатается
  на живых серверах.

  прочитаться как результат. `RunbookScript` разыгрывает машинные переменные один раз на прогон

  подтверждения, остановка на ненулевом коде (с опт-аутом на шаг), abort по Stop и по потере
  сессии; лок vault обрывает прогон (он держит разрешённые значения оставшихся шагов).

  как у сниппетов), Android — Ещё → Сценарии и пункт в меню терминала, общий `RunbookFormState`.
  В русском UI это «Сценарии» (EN `Runbooks`, ZH 运行手册 — устоявшиеся термины, не переводим). Диалог
  старта показывает все шаги с подставленными переменными (секреты замаскированы), панель
  прогресса — немодальная поверх терминала. v1: POSIX-шелл (`$?` + `printf`); без таймаута на
  шаг — зависший шаг снимается кнопкой Stop.

## Клиент: крупные ставки (кроме RDP)

- **SSH-сертификаты и short-lived keys.** CA-подписанные сертификаты, в
  перспективе OIDC → выпуск короткоживущего серта. Язык корпоративного
  zero-trust (Teleport/Boundary), естественное продолжение Teams.
- **TOTP в vault.** Хранить 2FA-секреты рядом с паролем, автоподставлять код в
  keyboard-interactive. В vault сейчас TOTP нет (совпадения по «one-time» — это
  transfer key пейринга). Vault и sync уже умеют всё нужное.

## Сервер синхронизации

- [x] **Каскадное удаление аккаунта** (бывший пункт «блок-лист удалённых аккаунтов»). ✅ Сделано
  (2026-07-26). При разборе выяснилось, что предпосылка пункта была неверной: «воскрешение» — не
  следствие дырявого удаления, а обычная повторная регистрация (id детерминирован, волт лежит на
  клиенте), и её закрывает `SKERRY_REGISTRATION=closed`. Настоящий баг был в другом: удаление
  чистило только `records`/`pairing`/`devices`/`accounts`, а `account_keys`, `team_members`,
  `team_scope_grants` и команды, которыми аккаунт владел, оставались — мусор на SQLite (FK не
  проверяются) и, судя по коду, отказ удаления на PostgreSQL. Теперь `deleteAccount` в одной
  транзакции чистит все восемь мест; команда владельца переходит старшему активному участнику
  (invited не в счёт — ключа у него нет), а без активных участников удаляется целиком со своими
  записями/областями/грантами; сводка попадает в аудит-строку. Побочно на клиенте: 403 получил свой
  `SyncException.Kind.FORBIDDEN` → `SyncFailureReason.Rejected` (раньше закрытая регистрация
  показывалась как «Ошибка протокола: server responded 403»). Блок-лист как отдельная сущность
  отклонён — дублировал бы `SKERRY_REGISTRATION=closed`.

  тумбстоун остаётся пустым как раньше. Восстановление кладёт запись обратно под тем же id
  через `Vault.putAtLeast` — версия поднимается выше тумбстоуна, иначе устройство, уже

  лимите любой участник, даже viewer, вытеснял историю чужих команд и админ-консоли;

  события пуша пишутся одной транзакцией (половина батча хуже, чем ничего: повтор
  пуша — no-op по LWW, и остаток уже не записался бы никогда), сбой аудита не валит
  сам пуш; поиск пространства хоста ушёл с UI-потока (это расшифровка всех TEAM-записей
  на каждый клик Connect); гейт приватности живёт в координаторе, а не в 4 местах.

  на серию), auth/admin/jwt/team-денаи, объём синка, WS-сессии (свой gauge, а не
  `ChangeNotifier.subscriptions` — там 3 подписчика на сессию), инвентарь, JVM/process/HikariCP
  под штатными именами. Инварианты, которые держат тесты: **в лейблах нет accountId/deviceId/
  recordId/teamId/scopeId/IP** (клиентские значения ⇒ рост реестра до OOM + утечка метаданных),
  `route` — только шаблон (`/admin/devices/{id}`), незамэтченные пути и `/console/*` не создают
  серию на запрос (`distinctNotRegisteredRoutes = false`), инвентарь считается **только** фоновой
  задачей (пул SQLite = 1 коннект, `SUM(LENGTH(blob))` на каждый скрейп конкурировал бы с push/pull),
  до первого сбора gauge = NaN, а не 0, и есть `skerry_inventory_last_success_time_seconds` —
  иначе устаревший gauge молча врёт. **`/readyz`** с фоновым пробером БД (гистерезис 3 сбоя → 503,
  1 успех → 200); `/healthz` намеренно не тронут — от него зависят Docker healthcheck, CI и
  клиентский `ping()` → self-heal, так что зависимость от БД превратила бы просадку в рестарт-цикл
  и шторм re-sync. `/metrics`, `/healthz`, `/readyz` исключены из `CallLogging`.

- **SSO/OIDC для Teams.** Вход через корпоративный IdP. Большая работа, но
  обязательный чекбокс для продаж командам.

## Связка клиент + сервер

- **Совместные сессии (session sharing).** Пригласить коллегу из команды в свой
  терминал (read-only или с вводом), релей через sync-сервер, E2E-шифрование
  ключом команды. Teams + запись сессий + сервер дают ~70% фундамента.
  Фича-магнит, которой нет почти ни у кого (tmate — отдельный инструмент).
- **Перенос сессии между устройствами.** Честный handoff сложен, но «тёплый»
  вариант дёшев: передать через sync текущий хост + cwd и открыть новую сессию
  в один тап («Continue on phone»).
- **Push-уведомления через сервер.** Триггеры на вывод и вердикты мониторинга
  («хост перестал отвечать») доставляются на телефон через sync-сервер — канал
  уже есть.
